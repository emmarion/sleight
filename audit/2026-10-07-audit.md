# Reference and self-hosted compiler audit — 2026-10-07

Audited revision: `f6b3cdd`. All of `DESIGN.md` was read before the audit. This report records observations and proposed fixes, not design decisions. No implementation or design files were changed.

Five new findings were reproduced. The most serious appears to be a self-hosted type-checker soundness defect: `slc` accepts a closed derivation of erased `False` that the reference rejects. Two further self-hosted evaluator defects silently truncate valid data. The reference findings concern its REPL and character-literal validation.

| ID | Severity | Affected path | Finding |
|---|---|---|---|
| A1 | Critical | `slc` checker | Telescope unification confuses a type with an `is` constraint, permitting erased `False` |
| A2 | High | `slc` evaluator and compile-time constants | Rope flattening silently discards data when its private fuel runs out |
| A3 | High | `slc` evaluator and compile-time constants | `list-to-array` silently truncates lists to one million elements |
| A4 | Medium | Reference REPL | Input framing counts parentheses inside strings and comments, and rejects multiline strings |
| A5 | Low | Reference reader/literal elaboration | Hexadecimal characters accept a trailing underscore instead of a second hex digit |

## A1. Telescope unification confuses `Ty` and `Is`

**Location:** [self/core.sl](../self/core.sl), `unify-sg`, lines 3513–3522, especially the mixed cases at 3518 and 3521. Reference comparison: [lib/env.ml](../lib/env.ml), lines 444–468.

**Reproducer:** [sg-confusion.sl](2026-10-07/sg-confusion.sl).

```scheme
(def-lvl L)
(def-fns L $ (erased reflect : (erased Type A) -> (erased A is r)) A)
(def-fns _ $ (erased use : (erased (Fn L (erased Type A) -> (erased A r)) f) -> (erased (False) impossible))
  (f (False)))
(let ((erased (False) contradiction)) (use reflect))
(def-fns _ $ (many absurd explode : -> (many (Nat) n)) contradiction)
explode
```

`reflect` returns the **type value** `A`: its return has type `Type` and is definitionally `A`. The higher-order argument of `use` instead promises an **inhabitant** of `A`. These signatures are different under DESIGN §§9, 11 and 12.

Observed results:

```text
reference: exit 1, argument 1 of use: type mismatch
slc compilation: exit 0, emits OCaml
slc --interpret: exit 1, runtime error: absurd code reached
compiled slc output: exit 1, runtime error: absurd code reached
```

The reference diagnostic shows the exact mismatch:

```text
expected (Fn L (erased Type A) -> (erased A r))
got      (Fn L (erased Type A) -> (erased A is r))
```

The mixed `SgTy`/`SgIs` branches of `unify-sg` compare their term payloads directly. Here both payloads are the same bound `A`, so the comparison succeeds despite the different entry forms. Calling the incorrectly accepted function at `(False)` then supplies the erased contradiction. Nothing needs to execute to construct that token.

This appears to invalidate the self-hosted checker's empty-type guarantee, rather than merely produce a bad diagnostic. The observed runtime failure is a consequence of an already accepted false proof. No custom extern declaration or missing user premise is involved.

**Suggested fix:** preserve the signature-entry constructor during unification, as the reference's structural comparison does; mixed `SgTy`/`SgIs` cases should not unify merely because their payloads match. Add negative tests in both directions, covering ordinary argument checking and forcing inside constructor/function signatures.

## A2. Rope conversion silently substitutes `REmpty` on fuel exhaustion

**Location:** [self/eval.sl](../self/eval.sl), `rope-walk` at 264–272, `rope-fields` at 273–278, and `flatten-value` at 280–282.

**Reproducer:** [rope-truncation.sl](2026-10-07/rope-truncation.sl).

The program tail-recursively wraps `RStr "x"` in 500,000 nodes of the form `RCat (REmpty) acc`. Flattening it must still produce `"x"`. A helper function keeps the large intermediate rope local; a run-position `let` computes and stores only the final string.

| Execution | Exit | Output |
|---|---:|---|
| Reference interpreter | 0 | `"x"` |
| Freshly rebuilt `slc --interpret` | 0 | `""` |
| OCaml emitted by that `slc`, compiled and executed | 0 | `""` |

`flatten-value` supplies an independent fixed fuel of 1,000,000. Both traversal functions return `REmpty` when their fuel reaches zero. Traversing a nested `RCat` consumes fuel through both functions, so the leaf disappears. The surrounding `flatten` call succeeds on the shortened rope, and the evaluator exposes the shortened string as a successful result.

This appears to violate DESIGN §31's requirement that host limitations produce a crash rather than a different value, and §42's requirement that an extern implementation agree with its model. In a run-position binding, the incorrect result is embedded in the emitted program. Its returned erased `Flat` evidence also no longer describes the actual string according to the source model; no separate derivation of `False` from this finding was attempted.

A nullary-function variant, where flattening runs in the emitted OCaml instead of at compile time, produced `"x"` through both backends while `slc --interpret` still produced `""`. That localizes the observed discrepancy to the self-hosted evaluator's conversion.

**Suggested fix:** either traverse the whole value or report exhaustion as a failure that aborts evaluation. Returning a valid empty rope is not an acceptable exhaustion result. Increasing the constant would only move the boundary.

## A3. `list-to-array` silently drops the suffix after one million elements

**Location:** [self/eval.sl](../self/eval.sl), `list-refs` at 137–145, especially 139; `ErListToArray` at 405–408.

**Reproducer:** [list-truncation.sl](2026-10-07/list-truncation.sl).

The program constructs 1,000,001 elements of `(Copy (Nat))`, converts the list with `list-to-array`, and reads the array length. The intermediate list and array are local to a helper; the final length is computed in run position.

| Execution | Exit | Output |
|---|---:|---|
| Reference interpreter | 0 | `1000001` |
| Freshly rebuilt `slc --interpret` | 0 | `1000000` |
| OCaml emitted by that `slc`, compiled and executed | 0 | `1000000` |

`ErListToArray` calls `list-refs 1000000`. At zero fuel, `list-refs` returns `Nil` as if the source list had ended. `array-block` then builds a successful array from the truncated list.

Besides returning the wrong length, this appears to break the contract that `(Array A xs)` contains exactly the elements of its index `xs` (DESIGN §44). The subsequent `array-length` still receives its ordinary erased `Length` evidence despite returning the shorter physical length. An attempted out-of-range access is not needed to demonstrate the defect and was not performed.

**Suggested fix:** handle exhaustion explicitly or remove this fuel-limited conversion. A2 and A3 share a failure pattern, but occur in separate conversion routines and need separate regression coverage. Other evaluator helpers that substitute ordinary values on exceptional paths merit a follow-up review; those paths are not counted as confirmed findings here.

## A4. The reference REPL frames input without lexing it

**Location:** [bin/main.ml](../bin/main.ml), lines 17–25.

**Reproducers:** [repl-string.in](2026-10-07/repl-string.in), [repl-comment.in](2026-10-07/repl-comment.in), and [repl-multiline.in](2026-10-07/repl-multiline.in).

Run each through:

```sh
_build/default/bin/main.exe --repl < audit/2026-10-07/repl-string.in
```

Observed behavior:

- A complete string literal `"("` causes another continuation prompt. At EOF, the buffered expression is silently discarded; no value or error is printed.
- A comment containing `(` followed by the expression `1` similarly causes the expression to be discarded at EOF.
- A valid multiline string, containing `hello`, a newline, and `world`, is prematurely submitted after its first line. The REPL reports an unterminated string and then an unbound name for the second line.

The first two files should respectively evaluate the string and `1`; DESIGN §§1 and 45 make parentheses inside strings/comments ordinary content. §45 explicitly permits literal newlines in strings.

`balance` counts every parenthesis byte, without tracking strings, escapes or comments. It also cannot recognize an unfinished string with balanced parentheses.

**Suggested fix:** use reader/tokenizer state to decide when an input form is complete, and report an unfinished buffered form at EOF. This is a REPL framing issue; file parsing was not observed to have the same behavior.

## A5. Reference hexadecimal character validation accepts `#\x1_`

**Location:** [lib/literal.ml](../lib/literal.ml), line 20.

**Reproducer:** [bad-hex-char.sl](2026-10-07/bad-hex-char.sl), containing only:

```scheme
#\x1_
```

Observed results:

```text
reference: exit 0, prints #\x01
slc --interpret: exit 1, malformed character literal #\x1_
```

DESIGN §45 requires exactly two hexadecimal digits after `x`. The reference checks the length and delegates validation to OCaml's `int_of_string_opt`; OCaml accepts the trailing underscore in `0x1_`. Thus an invalid source spelling is accepted by the reference but rejected by `slc`.

**Suggested fix:** validate both digit characters explicitly before conversion. This appears to be a language-conformance and portability defect, not a type-soundness failure.

## Validation, coverage and limits

- `dune build` passed.
- `dune test` reported **798 tests, 0 failures**.
- `self/bootstrap.sh one tests/*.sl` completed with **770 successful comparisons, 879 expected refusals, and 2 failures** (counts include repeated execution modes). Both failures were the existing `dump_context` test, once during compilation and once under `--interpret`. Its expected slot-class line has three groups; `slc` includes an additional `{h, _5}` group and extra temporary entries in the other groups. The reference matches the expectation. This diagnostic mismatch is recorded as a baseline failure, not an additional soundness finding. The initially attempted full bootstrap stopped because its BSD `time` invocation could not access `kern.clockrate` in the sandbox; the complete test sweep and the fixpoint were subsequently run separately.
- A1–A3 reproduced with a freshly extracted and natively compiled `slc`. Its generated OCaml for all three reproducers compiled successfully and produced the outcomes recorded above.
- The fresh `slc` compiled its own sources; that result was compiled and compiled the sources again. The two emitted source files were byte-for-byte identical. A self-hosting fixpoint therefore did not expose these defects.
- The review covered reference and self-hosted checking/unification, termination checks, erasure and ownership, coercions, cells/placement, evaluation/emission, and selected prelude/FFI/driver paths. Adversarial programs were used where a candidate could be made concrete; this was not an exhaustive proof or exhaustive state-space search.
- Existing `BUGS.md`, `audit/README.md`, `OPEN.md` and relevant prior findings were checked. Known all-erased-tail, special-form-head, FFI result-arity and slot-equality questions are not counted as new findings.
- No new closed derivation of `False` was found in the reference implementation. No new general ownership or termination counterexample was confirmed. This is a limit of the audit, not a consistency claim for `Type : Type`, unrestricted datatype signatures, or the open slot-equality questions.

The most urgent apparent repair is A1. A2 and A3 should follow because successful but incorrect evaluator results can cross the compile-time trust boundary described by DESIGN §29.
